## Apply order

1. **Merge `claude/consumption-caps`** (§7b, below). It is a fast-forward of `main`.
2. `git apply` 01 → 02 → 03 → 04 → 05 on top. 04 is optional; the others don't depend on it.
3. Migrations 0051–0054 then run in order. On the remote: `supabase db push` against nexo-ai, after a dry run on a branch.

The patches use migration numbers 0051–0054 because the branch already uses 0041–0050. If more hub migrations land first, rename the four files (the numbers inside them aren't referenced anywhere else).

## §7b: admit/settle are the existing hub commit `a5733df`, not a new patch

`/usage/admit`, `/usage/settle` and `reserved` in the balance come from hub commit **`a5733df`** ("tier caps, job admission, boost lane") on branch **`claude/consumption-caps`**. Chalito calls them, so they must be merged; no patch here re-implements them.

- **Conflicts with main: none.** `main` (`3f27ef3`) is an ancestor of both `a5733df` and the branch tip `d467b02`, and has no commits of its own since. The merge is a fast-forward.
- **The branch has moved past `a5733df`.** Its tip `d467b02` adds 31 commits on top (migrations 0048–0050, a 160% default margin, the RTMP relay VM, landing images, billing fixes). Merging the branch brings all of them. These patches target the tip because:
  - **5f62bfb** ("reservations hold the engine's estimate plus the margin") changes what `est_tokens` means, and patch 02 builds on it.
  - **0050** (`usage_cost_by_model`) is in patch 05's revoke list.
  - If the owner merges only `a5733df`: drop the `usage_cost_by_model` lines from 05, and drop the `admission*.ts` / `consumption.test.ts` hunks from 02 (keep its migration and doc line).
- **Contract change for engines (5f62bfb):** `est_tokens` is now the estimated provider cost ÷ 4 µ$, **before** the margin; the hub adds the margin when it reserves. Chalito currently sends estimates with the margin already included (`estimateBillable`, ×2.6), so it would reserve 2.6× too much once the branch is merged. Chalito handles it with `HUB_RESERVE_BASIS` (default `pre_margin`, matching 5f62bfb; `post_margin` only for a hub with a5733df alone, GO_LIVE 1.6a). For the store, patch 02 makes the hub reserve the price as-is.

## What each patch does, and how to test it on the hub

### 01: engine `chalito`
- **Changes:**
  - `definitions.ts` gets `createEngineIntegration({ slug: 'chalito', displayName: 'Chalito', postSsoPath: '/' })`.
  - The migration was generated by `node scripts/new-engine.mjs chalito "Chalito" --icon 🐻 --tier PRO --category AGENTS`, then the description was edited.
  - Row values: `external_url` `https://chalito.chalyb.com`, `admin_api_base` `https://api.chalito.chalyb.com`, `status` `coming_soon`, `tier_required` `PRO`.
- **Test:**
  - `select slug, status, tier_required, external_url, admin_api_base from engines where slug = 'chalito'`.
  - The tools grid shows a "Próximamente" card with the launch button disabled.
  - `/auth/launch/chalito` redirects to `/app/engines/chalito`, because the status isn't `active`.
- **Visible:** yes. The card appears in every PRO user's grid as coming soon. **Costs:** nothing.

### 02: `store.purchase` is already a price
- **Changes:**
  - The migration redefines `usage_billable_tokens` (0046's body plus one kind): `store.purchase`, like `boost.fee`, is billed `ceil(cost_usd_micros / 4)` with no margin.
  - `reserveWithMargin` returns the estimate unchanged for `operation = 'store.purchase'`, so the reservation is the price too.
  - The contract doc is updated to match.
- **Test:** `pnpm test` covers the reservation. To check the database, insert as `service_role` and read `billable_tokens`. Checked locally at the 160% default:

  | kind | cost_usd_micros | billable_tokens |
  |---|---|---|
  | `store.purchase` | 1,000,000 | 250,000 (= the price) |
  | `boost.fee` | 4,000 | 1,000 |
  | `voice.seconds` | 15,000 | 9,750 |
  | `llm.tokens` (100, no cost) | — | 260 |

- **Visible:** no. **Costs:** none by itself. It decides what Chalito store purchases debit from user balances.

### 03: Chalito device users stay out of the hub
Chalito's paired devices are Supabase Auth users with `app_metadata.chalito` (§7).
- **Changes:**
  - (a) `tg_handle_new_user` (0006's body plus a guard) returns early for them, so no `profiles` row and no welcome flow.
  - (b) A **restrictive** policy `chalito_device_fence`, `to authenticated`, `not coalesce((auth.jwt() -> 'app_metadata') ? 'chalito', false)`, goes on every RLS-enabled table in `public` and on `storage.objects`. It's created by a loop, so tables added later need it re-run or added by hand. Hub users are unaffected: the fence is restrictive and matches only device tokens.
- **Test** (checked locally, migrations applied on a Supabase-shaped database):
  - Insert an `auth.users` row with `raw_app_meta_data = '{"chalito":{}}'` → no `profiles` row. An ordinary user → a profile.
  - `select count(*) from pg_policies where policyname = 'chalito_device_fence'` → 31 in `public` + 1 on `storage.objects`.
  - With a device JWT, `engines` and `profiles` return 0 rows; with a hub JWT they return as before.
- **Visible:** no. **Costs:** nothing. It runs on the shared nexo-ai project, so the owner applies it.

### 04 (optional): forward `next` and `state` through `/auth/launch`
- **Changes:**
  - The new `launch-forward.ts` keeps `next` only if `safeNextPath` accepts it (relative, not `//`, no `\`, no control characters, ≤ 512 characters, checked raw and decoded).
  - It keeps `state` only if it's 16–128 base64url characters. Anything else is dropped and the launch goes ahead as before.
  - Both survive the `/sign-in` bounce. `getEngineLaunchUrl(engineId, forward?)` re-validates them (it's a server action) and hands them to the integration.
  - The factory puts `next` (overriding `postSsoPath`) and `state` on the engine's `/auth/sso` URL, never in the signed token.
- **Why:**
  - Chalito notification links (`/n/<nid>`) land on the right screen after sign-in, replacing its `chalito_next` cookie workaround.
  - Chalito already sends `?state=<nonce>` and checks it when the hub echoes it back (login-CSRF, review R-M1). Without the echo it falls back to the cookie alone.
  - Other engines are unaffected unless they start passing `next` or `state`.
- **Test:**
  - `pnpm test` (`tests/launch-forward.test.ts`: validation, query rebuild, URL shape with and without the params).
  - By hand: signed out, open `/auth/launch/<active engine>?next=/x&state=AAAAAAAAAAAAAAAAAAAA`. Sign in, and the engine's `/auth/sso` URL carries `next=%2Fx&state=…`.
  - `?next=https://evil.com` gives the old URL.
- **Visible:** only to engines that send the params. **Costs:** nothing.

### 05: hub security, server-only RPCs callable by anyone
- **The problem:**
  - Several `SECURITY DEFINER` functions are meant for `service_role` only. Their migrations say so with `revoke all … from public`.
  - On Supabase the project's default privileges grant `EXECUTE` on new `public` functions to `anon` and `authenticated` **directly**, so that revoke doesn't remove it.
  - Anyone with the publishable key can then call them via `/rest/v1/rpc/<name>`:
    - `admit_usage` and `settle_usage_reservation`: reserve against, or settle, **any user id**;
    - `usage_balance`;
    - `expire_usage_reservations`;
    - `engine_usage_metrics`, `compute_engine_royalties`, `compute_platform_token_stats`, `usage_cost_by_model`: every user's usage and revenue;
    - `usage_margin_percent` (it also kept its PUBLIC grant).
- **Already on main:** `compute_engine_royalties` and `compute_platform_token_stats` (0017) are on `main`, so if production has the default grants, **they're exposed today**. The others are exposed as soon as the branch merges.
- **The fix:** the migration revokes from `anon, authenticated` and re-grants `service_role`. Every hub call site already uses the admin (service-role) client. `is_admin()` stays (RLS calls it as the user). Trigger functions can't be called over RPC.
- **Check production first** (read-only, owner):
  ```sql
  select p.oid::regprocedure, has_function_privilege('anon', p.oid, 'execute') anon,
         has_function_privilege('authenticated', p.oid, 'execute') authd
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.prosecdef order by 1;
  ```
- **Test:** checked locally with Supabase's default privileges. Before: 11 definer functions executable by `anon` and `authenticated`. After: only `is_admin()` and the two trigger functions. `service_role` can still call `admit_usage`. An `authenticated` call to `usage_balance` gets "permission denied". The pricing trigger still fills `margin_percent` and `billable_tokens`.
- **Longer term:** `alter default privileges … revoke execute on functions from anon, authenticated`, so new functions start closed. That's not in this patch, because it changes behaviour for every future migration.
- **Visible:** no. **Costs:** nothing.

## Infrastructure and secrets (not patches; the owner applies them)

- **tfvars entry** in Chalyb `infra/terraform/terraform.tfvars`:
  ```hcl
  chalito = {
    display_name = "Chalito"
  }
  ```
  The module creates:
  - the `chalito` service account;
  - the secrets `chalito-admin-token`, `chalito-sso-secret` and `chalito-database-url`;
  - a public, scale-to-zero Cloud Run service (Chalito's `api`), with `ENGINE_SLUG`, `PUBLIC_URL=https://chalito.chalyb.com` and `CHALYB_BASE_URL` set.
- **Domain-mapping caveat:**
  - `enable_domain_mappings` is a single global flag. With it on, the module maps `chalito.chalyb.com` to Cloud Run, but that host must point at **Vercel** (Chalito's web/PWA, the engine's `external_url`).
  - Either leave the flag off for this apply and map `api.chalito.chalyb.com` → the `chalito` Cloud Run service by hand, or add a per-engine override to the module first.
  - Chalito's `api` doesn't use `PUBLIC_URL` as its own host.
- **Secret values:**
  - `chalito-sso-secret` = Vercel `CHALITO_SSO_SECRET`;
  - `chalito-admin-token` = Vercel `CHALITO_ADMIN_TOKEN` (also the bearer Chalito uses on `/api/engines/chalito/usage*`).
  - Chalito's `notifier` and `orchestrator` service accounts need `secretAccessor` on `chalito-admin-token`.

## Regenerating the patches

The patches are plain `git diff`s from a `git archive` export of `d467b02`. To check one:

```sh
mkdir /tmp/c && git -C ~/chalyb archive d467b02 | tar -x -C /tmp/c && cd /tmp/c && git init -q
for p in <this dir>/0*.patch; do git apply --check "$p" && git apply "$p"; done
pnpm install && pnpm typecheck && pnpm lint && pnpm test
```
