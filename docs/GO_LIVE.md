# Go live: from zero to a private beta

One ordered checklist for the owner. Do the phases in order; a phase only starts when the one before it verifies. It consolidates `docs/OPS.md`, `docs/RUNBOOK.md`, `docs/integrations/CHALYB_ENGINE.md` §§1–9, the owner items in `DEVIATIONS.md` and the READMEs. Where this file and those disagree, those are more detailed; this one is the order.

**Tags**
- **[cost]** spends money (a purchase, a subscription, or billable cloud or provider usage).
- **[visible]** is visible outside: a third party sees it, a phone rings, or a public URL changes.
- **Who** is **Owner** (you), **Hub** (whoever merges in `picassoglitch/chalyb`), or **Ops** (whoever runs the commands, possibly you).

Commands assume `PROJECT` = Chalyb's GCP project, `REGION=us-central1`, and a shell in the repo root (`~/chalito`) or in Chalyb's repo where noted.

### 2.4 decision: the shared migration ledger

nexo-ai has one migration ledger (`supabase_migrations.schema_migrations`), and it already holds the hub's versions (Chalyb `docs/infra/supabase.md`). `supabase db push` refuses to run when the database has versions the local folder doesn't, so two repos can't both push to it as they are: Chalito's push refuses because of the hub's versions, and once Chalito's are in, the hub's next push refuses because of Chalito's. That would block the hub's own deploys, not just Chalito's.

**Recommended: the hub carries Chalito's migration files.** A Chalyb PR copies `supabase/migrations/2026*.sql` from this repo into Chalyb's `supabase/migrations`, byte for byte, and the hub's normal `db push` applies them.
- **One ledger, one writer.** The ledger matches the files in one repo, so `supabase migration list` in Chalyb is the whole truth about nexo-ai, and the hub's deploys never trip over versions they don't know. That's what "one shared project" means in practice: the project's owner applies everything that goes into it, including Chalito's schemas. That's already the review model (CHALYB_ENGINE §7: hub sign-off on every shared-project change).
- **The hub's own tooling keeps working.** Supabase branches, `db push`, and (if the hub turns on GitHub branching) preview databases all see Chalito's schemas, so a hub change that breaks Chalito shows up on the hub's side first.
- **Chalito keeps the source.** Files are written and tested here (pgTAP and the rehearsal on the local stack, `scripts/nexo-ai-dryrun.sh --method hub` on a branch), and never edited in Chalyb. A new Chalito migration reaches nexo-ai only through a hub PR, which is the sign-off step anyway.
- **The cost, and how to handle it:**
  - The copies can drift. Copy, never edit, and compare checksums in the PR (`sha256sum supabase/migrations/2026*.sql` on both sides).
  - Ordering. Chalito's versions are timestamps (`20261004…`), which sort after the hub's four-digit ones. So a new hub migration (`0055`) is "before" the newest version already applied, and `supabase db push` needs `--include-all` to apply it. That's safe here, because the two sets don't depend on each other. Chalito's migrations create the `chalito` and `chalito_private` schemas, the `chalito_server` and `chalito_gateway` roles, `chalito-*` cron jobs and `realtime.messages` policies scoped to `chalito:*` topics, and they only `create extension if not exists` for `pg_cron` and `pgcrypto`. They touch no hub table. Better long term: the hub names new migrations with timestamps too (`supabase migration new` does), and then plain `db push` works.

**Other options (not recommended):**
- **Apply Chalito's files with `psql`, with no ledger entries.** It works today (`scripts/nexo-ai-dryrun.sh --method psql`), but nothing records what's applied. Every later migration needs someone to know which files already ran, and the migrations aren't all safe to re-run. It also hides Chalito's schemas from the hub's tooling.
- **Each repo pushes, then `supabase migration repair --status applied` the other's versions.** It keeps two writers on one ledger. Every push in either repo needs a repair step first, and one forgotten repair blocks the next deploy (the hub's included) until someone fixes the ledger by hand. It's the most fragile option.

**Rehearse it:** `HUB_DIR=<export of Chalyb with the patches> NEXO_AI_REF=uqcbziwdgbnzehipzjxp scripts/nexo-ai-dryrun.sh --method hub --yes`. It copies Chalito's files into a temporary copy of `HUB_DIR`, pushes once from there, and runs pgTAP and the rehearsal on the branch.
